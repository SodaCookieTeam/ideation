# ideation

소다맛쿠키 팀의 **아이디어 저장소**입니다. 떠오른 생각을 잃어버리지 않고 모아두고, 서로 붙여보고, 남길 것과 버릴 것을 골라내는 곳입니다.

코드는 여기에 없습니다. 구현은 별도 레포에서 진행하고, 이 레포는 "무엇을 만들지" 정하는 단계까지만 다룹니다.

## 왜 미리 모아두나

키로톤 본선(9/20)에서는 **주제가 당일 오전에 공개**되고, 아이디어 빌딩에 쓸 수 있는 시간은 1시간 30분 정도입니다. 그 자리에서 처음부터 짜내면 시간이 부족합니다.

그래서 미리 이렇게 해둡니다.

- 평소에 느낀 불편함, 만들어보고 싶던 것을 계속 적어둔다
- 주제가 나오면 쌓아둔 후보 중에서 **가장 가까운 것을 골라 변형**한다
- 이미 정리해둔 문제 정의와 핵심 기능을 그대로 재활용한다

즉, 목표는 "완성된 기획"이 아니라 **꺼내 쓸 수 있는 재료**를 쌓는 것입니다.

## 아이디어 올리는 방법

### 가볍게 던질 때 → Issue

한 줄이어도 괜찮습니다. 다듬는 건 나중에 합니다.

```
제목: [아이디어] 수업 자료 자동 요약해주는 도구
내용: PDF 강의자료 읽는 데 시간이 너무 걸림. 핵심만 뽑아주면 좋겠다.
```

### 정리가 된 아이디어 → `ideas/` 에 파일 추가

[`ideas/TEMPLATE.md`](ideas/TEMPLATE.md) 을 `ideas/YYYY-MM-DD-짧은-제목.md` 로 복사해서 채우고 PR을 올립니다.

파일 맨 위에는 아래처럼 front-matter 로 메타데이터를 답니다. 상태(`status`)는 여기서 관리합니다.

```markdown
---
title: 아이디어 제목
status: raw          # raw | exploring | shortlist | parked | dropped
owner: 깃허브핸들
created: YYYY-MM-DD
tags: [태그1, 태그2]
---

# 아이디어 제목
```

문서는 이 순서로 씁니다. **한 줄 요약 → 문제 → 해결 방식 → 핵심 기능 → 만들 수 있을까 → 참고.** 순서가 곧 판단 순서입니다.

**빈칸은 비워둬도 됩니다.** 다 채워야 올릴 수 있는 게 아니라, 채우다 막히는 부분이 곧 더 고민해야 할 지점입니다.

## 상태 관리

아이디어마다 상태를 붙입니다. Issue 에는 **라벨**로, 문서에는 앞머리의 front-matter **`status`** 로 붙이고 값은 같은 어휘를 씁니다.

| status | 뜻 |
| --- | --- |
| `raw` | 그냥 던진 것, 아직 검토 안 함 |
| `exploring` | 살펴보는 중 |
| `shortlist` | 본선에서 꺼내 쓸 후보 |
| `parked` | 지금은 아니지만 버리기는 아까움 |
| `dropped` | 접음 (이유를 적어두면 나중에 도움됨) |

`dropped` 도 **파일을 지우지 않고** 남깁니다. 왜 안 됐는지가 다음 아이디어의 힌트가 되고, 삭제하면 같은 아이디어를 두 달 뒤에 또 냅니다.

## 고를 때 보는 기준

본선에서 후보를 좁힐 때 이 순서로 봅니다.

1. **주제에 맞는가** — 아무리 좋아도 주제를 벗어나면 탈락
2. **하루 안에 데모가 나오는가** — 발표할 수 있는 형태까지 갈 수 있어야 함
3. **문제가 분명한가** — "누가 왜 이걸 쓰는지"를 한 문장으로 말할 수 있어야 함
4. **보여줄 게 있는가** — 발표에서 시연할 장면이 그려지는가

1번과 2번은 통과 조건이고, 3번과 4번으로 순위를 정합니다.

## 폴더 구조

```
ideation/
├── README.md            이 문서. 레포가 무엇이고 왜 있는지
├── CONTRIBUTING.md      올리는 절차 (브랜치·커밋·PR·리뷰)
├── CONVENTIONS.md       문서 규칙 (위치·이름·형식·문체)
├── ideas/               아이디어별 문서
│   └── TEMPLATE.md      아이디어 문서 템플릿
├── research/            사전 조사, 레퍼런스, 기술 검증 기록
├── assets/              이미지, 다이어그램
└── .github/             Issue·PR 템플릿
```

## 규칙 문서

| 문서 | 언제 보나 |
| --- | --- |
| [CONTRIBUTING.md](CONTRIBUTING.md) | 브랜치 이름, 커밋 메시지, PR·리뷰·승인 기준 |
| [CONVENTIONS.md](CONVENTIONS.md) | 파일을 어디에 넣나, 이름은 어떻게, 문서 형식과 문체 |

규칙이 아이디어를 막고 있다면 규칙이 틀린 겁니다. 고치는 PR을 올려주세요.

Kiro 로 문서를 쓸 때는 [`.kiro/steering/docs.md`](.kiro/steering/docs.md) 가 위 규칙을 자동으로 따르게 해줍니다.

## 태도

- **아이디어에 대한 비판은 환영, 사람에 대한 비판은 금지.** 코멘트는 아이디어를 향하게 씁니다.
- **거른 뒤에 던지지 말고, 던진 뒤에 거릅니다.** 별거 아닌 것 같아도 일단 올립니다.
- **남의 아이디어에 얹는 것을 권장합니다.** 반쯤 겹치는 두 아이디어가 붙어서 좋은 게 나오는 경우가 많습니다.
- **확인한 것과 추측을 구분해서 적습니다.** 안 해본 건 "확인 못 함" 이라고 씁니다. 본선 당일에 이 구분이 시간을 지켜줍니다.
- **결정은 기록으로 남깁니다.** 왜 이걸 골랐고 왜 저건 접었는지 적어두면 발표 자료를 쓸 때 그대로 씁니다.
