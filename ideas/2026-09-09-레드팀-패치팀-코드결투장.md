# 레드팀 대 패치팀 코드 결투장

## 한 줄 요약
학생 프로젝트 코드에 뚫릴 구멍이 있는지 몰라 그냥 제출하는 문제를, 공격 에이전트가 실패하는 테스트로 취약점을 증명하고 수정 에이전트가 패치하고 테스트 러너가 심판을 보게 해서 해결한다.

## 문제
- 캡스톤·해커톤 코드를 제출하는 학생
- "돌아가니까 됐다"로 넘기고, 리뷰를 받아도 "여기 위험해 보임" 수준의 지적만 얻는다.
- 실제로 뚫리는지 확인할 방법이 없어서 지적을 무시하거나 과하게 고친다.

## 해결 방식
1. **정찰관** — 레포를 훑어 공격 표면 후보 목록을 만든다
2. **레드팀** — 후보마다 **실패하는 테스트 코드**를 작성해 실행한다. 테스트가 통과해버리면 취약점 주장은 기각된다
3. **패치팀** — 살아남은 실패 테스트를 통과시키는 최소 수정 diff를 낸다
4. **심판** — 기존 테스트와 새 테스트를 전부 실행한다. 회귀가 생기면 패치를 롤백하고 패치팀에 반송한다

사람은 패치 diff를 승인하거나 거절한다.

### 왜 역할을 나누는가
LLM 한 번 호출로 받은 보안 지적은 검증이 없어 오탐이 섞이고, 사람이 하나하나 확인해야 한다. "실패 테스트로 증명하고 실행으로 심판한다"는 규칙이 있어야 주장이 사실로 승격된다. 회귀 롤백이라는 되돌리기 장면도 여기서 나온다.

## 핵심 기능
- [ ] 취약점 주장 → 실패 테스트 실행으로 자동 채택/기각 (최소 기능)
- [ ] 패치 적용 후 전체 테스트 실행, 회귀면 자동 롤백 및 재시도
- [ ] 결투 기록 타임라인 — 주장 / 증명 / 패치 / 판정
- [ ] 사람 승인 게이트

## 만들 수 있을까
- 필요한 기술: LLM, pytest, git(diff와 체크아웃 기반 롤백), 정적 분석 보조
- 하루 안에 데모까지: **가능.** 대상 레포를 미리 준비한 파이썬 소형 프로젝트 하나로, 취약점 2건으로 못 박고 테스트 실행을 로컬 pytest로 제한하면 한 사이클을 짧게 끊을 수 있다.
- bandit·semgrep 룰셋의 사용 조건은 **확인 못 함.** 없어도 성립하도록 설계한다.
- 걸림돌
  - **임의 생성 코드를 실행한다.** 별도 작업 디렉터리와 타임아웃, 화이트리스트가 필수다. 격리 없이는 데모 자체가 위험하다.
  - 패치와 회귀 루프가 2회 이상 돌면 시연 대기가 30초를 넘는다. 루프 상한을 걸어야 한다.
  - 테스트 프레임워크가 없는 레포에는 쓸 수 없다.

## 시연 장면
심사위원 앞에서 취약점 주장 3개가 뜬다. 하나가 테스트 통과로 "기각" 처리되며 회색으로 죽는다. 남은 2개에 대해 diff가 뜨고 사람이 승인을 누르자 테스트 러너가 돌고, 기존 테스트 하나가 깨져 빨간 줄이 뜬다. 화면에 **"롤백"** 배너가 뜨고 패치팀이 두 번째 패치를 내놓아 전부 초록이 된다.

## 참고
- 기존 AI 코드 리뷰는 지적을 텍스트로 뱉고 끝난다.
- 이 아이디어는 실행 결과가 심판이라 오탐이 화면에서 죽고, **실패했을 때 되돌리는 과정 자체가 시연물**이다.
- 심사위원이 개발자일 경우 공감이 가장 빠른 후보다. 반대로 주제가 사회문제 계열로 나오면 후순위다.
