# 틈새상점: 유휴시간 팝업 오케스트레이터

## 한 줄 요약
카페·공방의 비수 시간과 학생 동아리·창작자의 단기 행사 공간 수요를 조건 기반으로 연결하고, 점주 승인 전까지 탐색·비교·운영 준비를 대신하는 에이전트다.

## 문제
- 카페·공방 점주는 손님이 적은 시간대의 임대료와 인건비를 부담하지만, 그 시간을 별도 상품으로 구성하고 판매하기 어렵다.
- 학생 동아리·창작자는 전시, 소규모 공연, 워크숍, 플리마켓을 열 공간을 찾을 때 여러 점포에 같은 질문을 반복한다.
- 양쪽은 인원, 시간, 예산뿐 아니라 소음, 전기 용량, 취식, 장비 반입, 정리 시간 같은 조건을 늦게 확인해 협의가 자주 되돌아간다.
- 현재는 지도 검색, SNS 메시지, 전화, 스프레드시트로 버티며, 후보 비교와 견적 협의의 기준이 사람마다 다르다.
- 허가, 소방, 소음, 영업신고 범위, 계약 책임을 확인하지 않고 연결하면 점주와 주최자 모두에게 손해가 생길 수 있다.
- 유휴시간 연결이 실제 매출 증가나 공간 탐색 시간 단축으로 이어지는지는 확인 못 함이다.

## 해결 방식
점포가 공개한 유휴시간과 운영 조건을 구조화하고, 행사 요청을 같은 형식으로 받아 하드룰을 먼저 적용한 뒤 설명 가능한 후보 비교안과 운영 문서를 만든다.
하루 MVP는 합성 점포와 합성 행사 요청만 사용하며, 실제 지도·예약·결제·메시지 API 연동 가능 여부는 확인 못 함이다.

### 에이전트 루프
1. 에이전트가 주최자에게 행사 유형, 예상 인원, 시작·종료·준비·철수 시간, 총예산, 소음 수준, 필요 전력, 취식, 주류, 장비 반입, 접근성 조건을 질문한다.
2. 답이 비었거나 서로 충돌하면 후보를 찾기 전에 추가 질문하고, 답을 받지 못한 항목은 `미확인`으로 표시한다.
3. 합성 점포 목록에서 영업 공백 시간, 수용 인원, 최소 대관료, 소음 허용치, 전기 용량, 취식 정책, 금지 행사 유형을 기준으로 후보를 탐색한다.
4. 수용 인원 부족, 시간 불일치, 예산 초과, 소음 초과, 전기 부족, 취식 불가 같은 하드룰 위반 후보를 제외하고 제외 이유를 남긴다.
5. 통과 후보를 비용, 이동 편의, 준비 여유, 조건 적합도 순으로 비교하되, 점수의 가중치는 데모용 가정이라고 표시한다.
6. 후보별 고정 대관료안과 기본 매출배분안을 만들고, 예상 매출은 참석 인원과 객단가를 입력한 가정치로만 계산한다.
7. 점주에게 요청 조건, 위험 표시, 견적안, 매출배분안, 취소 조건 초안을 보여주고 승인·수정·거절 중 하나를 받는다.
8. 점주가 승인한 경우에만 모의 예약 상태를 만들고 데모 캘린더에 준비·행사·철수 시간을 반영한다.
9. 행사 유형과 점포 조건에 맞춰 당일 연락망, 입장, 장비, 전기, 소음, 위생, 쓰레기, 원상복구, 정산 항목이 포함된 운영 체크리스트를 만든다.
10. 조건이 바뀌면 하드룰 검사부터 다시 실행하고, 기존 승인과 모의 예약을 자동 확정하지 않는다.

### 3분 데모
- 0:00~0:30에 학생 창작자가 25명 규모의 저녁 전시, 20만 원 예산, 간단한 취식, 낮은 소음, 벽면과 콘센트 필요 조건을 입력한다.
- 0:30~1:00에 에이전트가 철수 시간과 장비 소비전력을 추가 질문하고 요청서를 완성한다.
- 1:00~1:30에 합성 점포 다섯 곳을 탐색해 정원 부족 한 곳, 취식 불가 한 곳, 전기 부족 한 곳을 제외 이유와 함께 보여준다.
- 1:30~2:00에 남은 두 곳의 총비용, 이동 편의, 조건 적합도, 고정 대관료안과 매출배분안을 나란히 비교한다.
- 2:00~2:30에 점주 화면에서 한 후보의 종료 시각과 보증금 조건을 수정한 뒤 승인한다.
- 2:30~3:00에 모의 예약과 데모 캘린더 반영, 행사별 운영 체크리스트 생성을 보여준다.

### 승인과 안전 원칙
- 에이전트는 추천과 초안을 만들지만 점주 승인 없이 예약, 일정 반영, 외부 연락을 확정하지 않는다.
- 법적 허가, 소방 수용 인원, 보험, 주류 판매, 음악 사용, 식품 취급 조건은 자동 판정하지 않고 `현장 확인 필요`로 표시한다.
- 하드룰 위반 후보는 높은 예상 수익을 이유로 다시 포함하지 않는다.
- 견적과 매출배분은 계약이 아니라 협의 초안이며, 실제 계약서 검토와 당사자 확인이 필요하다.
- 개인정보는 데모에 넣지 않고 합성 이름과 연락처만 사용한다.

## 핵심 기능
### 하루 MVP
- [ ] 행사 조건을 대화형 폼으로 수집하고 누락·충돌 항목을 재질문한다.
- [ ] 합성 점포 5~10곳을 검색하고 하드룰 위반 후보와 제외 이유를 보여준다.
- [ ] 통과 후보를 표로 비교하고 고정 대관료안과 매출배분안의 계산 근거를 보여준다.
- [ ] 점주가 승인·수정·거절할 수 있는 승인 화면을 제공한다.
- [ ] 승인된 건에 한해 모의 예약과 데모 캘린더 일정을 생성한다.
- [ ] 행사별 운영 체크리스트를 생성한다.

### 후속 확장
- [ ] 점포가 실제 유휴시간과 조건을 관리하는 온보딩 화면을 추가한다.
- [ ] 지도, 캘린더, 전자서명, 메시지, 결제 서비스 연동을 검증한 뒤 단계적으로 추가한다.
- [ ] 과거 승인·거절 이유를 바탕으로 추천 기준을 조정하되 하드룰은 학습 대상에서 제외한다.
- [ ] 접근성, 장비 대여, 청소, 보험 등 주변 운영 파트너를 연결한다.
- [ ] 노쇼율, 협의 소요 시간, 유휴시간 회수매출을 측정해 추천 효과를 검증한다.

### 제외 범위
- [ ] 실제 예약 확정, 결제, 보증금 수납, 환불은 하지 않는다.
- [ ] 법률·소방·영업 허가의 적법성을 대신 판단하지 않는다.
- [ ] 점주나 주최자를 대신해 계약에 동의하거나 외부 메시지를 자동 발송하지 않는다.
- [ ] 공개되지 않은 점포 영업 데이터나 개인 위치 정보를 수집하지 않는다.

## 만들 수 있을까
### 필요한 기술/API
- 대화형 조건 수집 UI, 규칙 기반 필터, 후보 비교표, 견적 계산기, 승인 상태 머신, 체크리스트 생성기가 필요하다.
- 합성 JSON 데이터와 로컬 캘린더 UI만으로 핵심 루프의 하루 데모 구현은 가능하다고 가정한다.
- LLM은 추가 질문과 설명·체크리스트 초안 생성에 사용할 수 있지만, 호출 품질과 비용은 확인 못 함이다.
- 실제 지도 검색, 캘린더 쓰기, 예약, 결제, 전자서명 API의 사용 조건과 심사 기간은 확인 못 함이다.

### 하루 안에 데모까지 갈 수 있는가
- 오전에는 합성 점포 스키마, 행사 입력 폼, 하드룰 엔진을 구현한다.
- 오후에는 후보 비교, 견적·매출배분 계산, 점주 승인 상태, 모의 캘린더를 연결한다.
- 마감 전에는 고정된 성공 시나리오와 하드룰 탈락 시나리오를 각각 한 번 실행하고 3분 흐름을 리허설한다.
- 자연어 입력 전체를 안정적으로 처리하기보다 선택형 입력과 제한된 자유 입력을 함께 쓰는 것이 하루 MVP에 안전하다고 가정한다.

### 걸림돌과 안전장치
| 걸림돌 | 안전장치 |
| --- | --- |
| 점포별 허가와 영업신고 범위가 다름 | 자동 적법 판정을 금지하고 점주 확인 항목과 관할 기관 확인 필요 표시를 둔다. |
| 소방 수용 인원과 비상 동선 정보가 부정확할 수 있음 | 점주가 등록한 보수적 정원만 하드룰에 사용하고 현장 점검 전 확정을 막는다. |
| 공연·행사 소음이 이웃 민원으로 이어질 수 있음 | 소음 등급과 종료 시각을 하드룰로 두고 담당자 연락망과 즉시 중단 절차를 체크리스트에 넣는다. |
| 전기 과부하와 장비 파손 위험이 있음 | 필요 소비전력을 받고 미확인 시 추천에 경고를 표시하며 실제 배선 확인을 요구한다. |
| 취식·주류·식품 취급 책임이 모호할 수 있음 | 허용 범위와 책임 주체를 승인 전에 명시하고 관련 허가 미확인 시 해당 활동을 제외한다. |
| 견적이나 매출 예상이 사실처럼 받아들여질 수 있음 | 모든 예상값에 입력값, 계산식, 가정 표시를 붙이고 최소 보장으로 표현하지 않는다. |
| 취소·노쇼·원상복구 분쟁이 생길 수 있음 | 취소 시점, 보증금, 파손, 청소, 정산 기준을 계약 전 확인 목록으로 제시한다. |
| 에이전트가 조건 변경 후 예전 승인을 재사용할 수 있음 | 핵심 조건 변경 시 승인을 무효화하고 점주 재승인을 요구한다. |

## 참고
- 비슷한 대관·팝업 중개 서비스의 수수료, 책임 범위, 보험 구조는 확인 못 함이다.
- 캠퍼스타운 점포의 실제 비수 시간과 학생 창작자의 공간 수요 규모는 사용자 인터뷰로 확인해야 한다.
- MVP의 후보 점포, 가격, 예상 방문객, 예상 매출은 모두 합성 데이터와 데모용 가정으로 구성한다.
