# 스크린리더 여정 통과 테스트 에이전트

## 한 줄 요약
접근성 점수는 통과인데 시각장애인이 실제로는 결제까지 못 가는 문제를, 에이전트가 접근성 트리만 보고 사용자 여정을 시도해 막힌 지점과 수정 코드를 내놓는 방식으로 해결한다.

## 문제
- 스크린리더 사용자와 그 사이트를 만드는 개발팀
- 지금은 Lighthouse 점수 90점을 받고 안심한다. 그런데 라벨 없는 아이콘 버튼 하나 때문에 장바구니에서 멈춘다.
- **점수는 통과인데 여정은 실패한다.** 규칙 위반 목록과 "목표를 달성할 수 있는가"는 다른 질문이다.

## 해결 방식
1. 목표 여정을 입력한다 — "상품 검색 → 장바구니 → 결제 시작"
2. 에이전트가 **접근성 트리만 사용해** 단계를 시도한다. 시각 정보를 쓰지 않는 것이 규칙이다
3. 실패 지점과 그때 낭독될 문구를 재현한다
4. 해당 DOM에 대한 수정 diff를 제안하고, 적용 후 다시 돌려 통과를 확인한다

## 핵심 기능
- [ ] 목표 여정 입력과 접근성 트리 기반 단계 시도 (최소 기능)
- [ ] 실패 지점 + 낭독 문구 재현
- [ ] 수정 diff 제안과 재실행 통과 확인
- [ ] 단계 수 상한과 실패 기록

## 만들 수 있을까
- 필요한 기술: 브라우저 자동화의 접근성 트리 조회, LLM(다음 행동 결정과 수정 제안), WCAG 항목 매핑
- 하루 안에 데모까지: **가능.** 대상 사이트를 우리가 만든 샘플 상점으로 고정하면 안정적이다. Kiro로 코드를 고치는 흐름과 자연스럽게 붙는다.
- **WCAG 전수 준수 판정은 불가능하다.** 완전한 접근성 검증은 보조기술 실제 테스트와 전문가 검토가 필요하다. 이 도구는 "특정 여정이 막혔는지"만 판정한다고 화면에 명시한다.
- 걸림돌
  - 에이전트가 트리 정보만으로 헤매다 루프에 빠진다. 단계 수 상한과 실패 기록이 필요하다.
  - 남의 사이트를 대상으로 시연하면 로그인과 봇 차단에 걸린다. 자체 샘플 상점을 쓴다.

## 시연 장면
화면을 반으로 나눠 왼쪽은 실제 브라우저, 오른쪽은 "스크린리더가 읽는 말" 텍스트 스트림을 흘린다. 에이전트가 진행하다가 "버튼"이라고만 읽히는 지점에서 빨간 정지 카드가 뜨고 "여기서 시각장애 사용자는 결제로 갈 수 없다"가 표시된다. 이어서 `aria-label`을 넣는 diff를 보여주고 다시 돌려 여정이 끝까지 통과한다.

## 참고
- axe, Lighthouse, WAVE는 규칙 위반 목록을 준다.
- 이 아이디어는 그 위반 때문에 **목표 달성이 막혔는가**를 여정 단위로 판정하고 수정안까지 낸다.
- 접근성과 개발자 도구가 교차하는 자리라, 심사위원 구성이 어느 쪽이든 걸린다.
