# 멀티 에이전트 지원금·복지 비서 (5-에이전트 협업 구조)

## 한 줄 요약
"내가 받을 수 있는 돈이 뭔지" 모르는 시민을 위해, 서로 역할이 다른 5개의 AI 에이전트가
협업해서 상담 → 혜택 수집 → 자격 매칭 → 서류 작성 → 마감 관리까지 끝까지 대신 처리해주는 서비스.

## 왜 이 주제인가 (해커톤 조건 정합성)
- **에이전트를 실제로 쓴다**: 단일 챗봇이 아니라, 역할이 나뉜 여러 에이전트가 서로 결과를 주고받는
  멀티 에이전트 오케스트레이션 구조다. "에이전트다움"을 심사위원에게 명확히 보여줄 수 있다.
- **5명이 한 번에 병렬 개발 가능**: 에이전트 5개를 각자 1명씩 맡으면 초반부터 동시에 작업할 수 있다.
  에이전트 간 통신은 공용 인터페이스(메시지/상태 스키마)로 미리 합의만 하면 서로를 기다리지 않아도 된다.
- **실용성**: 실제로 돈이 걸린 문제라 공감대가 크고, 데모 임팩트가 강하다.

## 문제
- 청년·사회초년생·1인가구·일반 시민이 겪는 문제
- 정부/지자체 지원금·복지 혜택이 수백 개로 흩어져 있어 자신에게 뭐가 해당되는지 모른다
- 조건이 복잡해 자격 판단이 어렵고, 서류 준비와 마감 관리가 번거롭다
- 결국 **"몰라서 못 받는 돈"** 이 생긴다 (커뮤니티/블로그에서 반복 확인된 표현)

## 해결 방식: 5개 에이전트의 협업
사용자는 하나의 채팅 창과 대화하지만, 뒤에서는 오케스트레이터가 4개의 전문 에이전트를 조율한다.

```
                    ┌─────────────────────────┐
   사용자  ◄──────► │  ① 오케스트레이터 에이전트  │
                    │  (대화 흐름·라우팅·통합)     │
                    └───────────┬─────────────┘
             ┌──────────────────┼──────────────────┐
             ▼                  ▼                  ▼
   ② 프로필/상담 에이전트   ③ 혜택 수집 에이전트   ④ 자격 매칭 에이전트
   (질문으로 상황 파악)     (공고 크롤링·정규화)   (조건 대조·해당 여부 판단)
                                                    │
                                                    ▼
                                          ⑤ 서류·마감 에이전트
                                          (신청서 초안·체크리스트·마감 알림)
```

1. **② 프로필/상담 에이전트** — 사용자에게 필요한 것만 질문해 프로필(나이·지역·소득·주거·취업상태 등)을 구조화
2. **③ 혜택 수집 에이전트** — 복지로/정부24/온통청년 등에서 공고를 수집하고 공통 스키마로 정규화
3. **④ 자격 매칭 에이전트** — 프로필과 혜택 조건을 대조해 "해당/미해당/애매" 판정 + 근거 설명
4. **⑤ 서류·마감 에이전트** — 혜택별 필요 서류 체크리스트, 신청서 초안 문구, 마감일 알림 생성
5. **① 오케스트레이터 에이전트** — 사용자 대화를 받아 어느 에이전트를 언제 호출할지 라우팅하고 결과를 통합

## 핵심 기능 (MVP)
- [ ] 대화로 사용자 프로필 수집 및 구조화 (② 담당)
- [ ] 지원금 공고 2~3개 소스 수집·정규화 (③ 담당)
- [ ] 프로필-조건 매칭 및 해당 여부 근거 제시 (④ 담당)
- [ ] 혜택별 서류 체크리스트 + 신청서 초안 생성 (⑤ 담당)
- [ ] 에이전트 라우팅·결과 통합·채팅 UI (① 담당)
- [ ] (있으면 좋음) 마감 알림, 애매 케이스 재질문

## 5명 역할 분담 (에이전트 = 1인 1담당)
| 담당 | 에이전트 | 주 작업 | 인접 인터페이스 |
|------|----------|---------|-----------------|
| A | ① 오케스트레이터 + 프론트 | 라우팅 로직, 채팅 UI, 결과 통합 | 모든 에이전트의 입출력 스키마 |
| B | ② 프로필/상담 | 질문 설계, 프로필 JSON 스키마 | ①에 프로필 전달 |
| C | ③ 혜택 수집 | 크롤링/파싱, 혜택 JSON 정규화 | ④에 혜택 목록 전달 |
| D | ④ 자격 매칭 | 조건 대조 로직, 판정 근거 생성 | ②·③ 결과 입력, ⑤로 전달 |
| E | ⑤ 서류·마감 | 서류 체크리스트, 신청서 초안, 알림 | ④ 판정 결과 입력 |

> 병렬 개발 핵심: 시작할 때 **에이전트 간 주고받을 JSON 스키마(프로필/혜택/판정/문서)** 를 먼저 합의하면,
> 각자 mock 데이터로 독립 개발하다가 마지막에 붙이면 된다. 서로를 기다릴 필요가 없다.

## 만들 수 있을까
- 필요한 기술/API
  - LLM (상담·매칭 근거·문서 생성): OpenAI / Claude 등
  - 오케스트레이션: LangGraph / 자체 라우터 등 멀티 에이전트 프레임워크
  - 크롤링: Playwright / BeautifulSoup (소스 2~3개로 제한)
  - 프론트: 웹 채팅 UI (React 등)
- 하루 안에 데모까지 갈 수 있는가
  - 스키마를 먼저 고정하고 크롤링 소스를 2~3개로 좁히면 가능
  - 크롤링이 막히면 ③은 초기엔 정적 시드 데이터로 대체하고 실시간 수집은 후순위로
- 걸림돌
  - 공공기관 사이트마다 구조가 달라 크롤러 유지보수 부담 → 소스 최소화로 대응
  - 자격 판정의 정확성 → "안내/초안 보조" 로 포지셔닝, 최종 확인은 사용자 몫으로 명시
  - 개인정보 처리 → 프로필은 로컬/세션 범위로 최소 수집
