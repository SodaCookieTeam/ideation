# 개발 착수 계획

확정 주제 **멀티 에이전트 지원금·복지 알림 비서** 를 5명이 병렬로 개발하기 위한 사전 합의 문서다.

아이디어 문서가 "무엇을 만들지"라면 이 문서는 **"누가 무엇을 어떤 규격으로 만들지"** 다.
근거가 되는 문서는 [멀티 에이전트 지원금·복지 비서](../ideas/2026-09-09-멀티에이전트-지원금-복지-비서.md),
[숨은 지원금 헌터](../ideas/2026-09-09-숨은-지원금-헌터.md),
[문제 근거 SNS 조사](지원금-헌터-문제근거-SNS조사.md),
[선별 기록](선별-기록.md) 이다.

작성: 2026-09-09

## 가장 먼저 할 일

**코드를 쓰기 전에 아래 스키마 4개를 확정한다.** 이것만 고정되면 5명이 서로를 기다리지 않는다.

`Profile` / `Benefit` / `Verdict` / `Document`

스키마 합의에 30분을 쓰는 것이 아깝게 느껴지더라도, 이걸 건너뛰면 마지막 통합에서 두 시간을 잃는다.
[선별 기록](선별-기록.md)이 정리한 규칙 그대로다. 붙이는 시점의 비용을 앞으로 당기는 것이다.

## 만들 것과 안 만들 것

### MVP 경계

| 만든다 | 만들지 않는다 |
| --- | --- |
| 대화로 프로필 수집 | 로그인, 회원가입, 계정 |
| 혜택 데이터 2~3개 소스 | 실시간 크롤링 스케줄러 |
| 조건 매칭과 판정 근거 표시 | 마이데이터, 오픈뱅킹 연동 |
| 서류 체크리스트와 신청서 문구 초안 | 실제 신청 제출, 기관 API 연동 |
| 마감일 계산과 화면 내 알림 | 푸시 알림, 이메일 발송 |
| 청년 대상 시연 시나리오 1개 | 전 연령 전체 혜택 커버 |

연동이 걸린 것은 전부 뺐다. [선별 기록](선별-기록.md)의 관찰 그대로,
연동이 필요한 후보는 예외 없이 하루 데모가 무너진다.

### 이번에 안 붙일 것을 미리 못 박는 이유

발표에서 "이건 아직 안 됩니다"를 말하는 것보다,
**"이번 범위는 여기까지입니다"** 를 미리 정해두고 말하는 것이 신뢰를 얻는다.

## 시스템 구조

```text
                    사용자 (웹 채팅)
                          │
                          ▼
              ┌───────────────────────┐
              │  ① 오케스트레이터       │   라우팅과 결과 통합
              │     (코드, LLM 아님)    │
              └───────────┬───────────┘
          ┌───────────────┼───────────────┐
          ▼               ▼               ▼
   ② 프로필/상담     ③ 혜택 수집      ④ 자격 매칭
   Profile 생성      Benefit[] 생성   Verdict[] 생성
                                          │
                                          ▼
                                   ⑤ 서류·마감
                                   Document 생성
```

**오케스트레이터는 LLM 이 아니라 코드다.** 순서를 고정 파이프라인으로 돌린다.
조율 판단까지 LLM 에 맡기면 디버깅이 불가능해지고 하루 안에 안 끝난다.

호출 순서는 다음과 같다.

1. ② 가 대화로 `Profile` 을 채운다
2. ③ 이 `Benefit[]` 을 반환한다 (② 와 병렬 실행 가능)
3. ④ 가 `Profile` 과 `Benefit[]` 을 받아 `Verdict[]` 을 만든다
4. ⑤ 가 `Verdict[]` 중 해당 건에 대해 `Document` 를 만든다

## 공용 스키마

아래는 **초안이다.** 착수 회의에서 확정하고, 확정 후에는 규칙에 따라서만 바꾼다.

### Profile

```json
{
  "age": 24,
  "region": { "sido": "서울특별시", "sigungu": "성북구" },
  "householdType": "1인가구",
  "employmentStatus": "구직중",
  "incomeBracket": "중위소득 100% 이하",
  "isStudent": true,
  "housingType": "월세",
  "answeredAt": "2026-09-09T10:00:00+09:00",
  "unknownFields": ["incomeBracket"]
}
```

`unknownFields` 가 핵심이다. 모르는 값을 그럴듯하게 채우지 않고 명시한다.
④ 는 이 목록을 보고 판정을 `확인 필요` 로 내린다.

### Benefit

```json
{
  "id": "seoul-youth-rent-2026",
  "title": "청년 월세 지원",
  "agency": "서울특별시",
  "amount": { "value": 200000, "unit": "월", "maxTotal": 2400000 },
  "conditions": [
    { "field": "age", "op": "between", "value": [19, 39] },
    { "field": "region.sido", "op": "eq", "value": "서울특별시" },
    { "field": "housingType", "op": "eq", "value": "월세" }
  ],
  "deadline": "2026-10-31",
  "applyUrl": "https://...",
  "requiredDocuments": ["임대차계약서", "주민등록등본"],
  "sourceUrl": "https://...",
  "fetchedAt": "2026-09-09"
}
```

`conditions` 를 **기계가 읽을 수 있는 형태**로 두는 것이 중요하다.
문장으로 두면 ④ 가 LLM 으로 해석해야 하고, 그 순간 판정이 흔들린다.

`fetchedAt` 은 반드시 넣는다. 화면에 "언제 확인한 정보인지"를 표시해야 한다.

### Verdict

```json
{
  "benefitId": "seoul-youth-rent-2026",
  "result": "eligible",
  "reasons": [
    { "field": "age", "matched": true, "detail": "24세, 조건 19~39세" },
    { "field": "housingType", "matched": true, "detail": "월세 거주" }
  ],
  "blockers": [],
  "needsConfirm": ["incomeBracket"],
  "estimatedAmount": 2400000
}
```

`result` 값은 셋으로 고정한다.

| 값 | 뜻 | 화면 표시 |
| --- | --- | --- |
| `eligible` | 조건을 모두 만족 | 해당 가능성 있음 |
| `needs_confirm` | 일부 조건을 판단할 수 없음 | 확인 필요 |
| `ineligible` | 조건에 명확히 어긋남 | 해당 없음 |

`eligible` 을 화면에 **"신청 가능"으로 쓰지 않는다.**
자격 판정이 틀렸을 때의 책임 문제를 피하고, 최종 확인은 사용자에게 남긴다.

### Document

```json
{
  "benefitId": "seoul-youth-rent-2026",
  "checklist": [
    { "name": "임대차계약서", "where": "본인 보관", "done": false }
  ],
  "draftText": "안녕하십니까. 청년 월세 지원 신청과 관련하여...",
  "deadline": { "date": "2026-10-31", "dDay": 52 },
  "applyPath": "서울주거포털 온라인 신청"
}
```

`dDay` 는 **코드로 계산한다.** LLM 이 날짜를 계산하면 발표에서 신뢰를 잃는다.
금액 합산도 같다.

## 파트 분배

| 담당 | 파트 | 만드는 것 | 입력 | 출력 |
| --- | --- | --- | --- | --- |
| A | ① 오케스트레이터 + 프론트 | 파이프라인 코드, 채팅 UI, 결과 카드, 근거 펼치기 | 사용자 입력 | 화면 |
| B | ② 프로필/상담 에이전트 | 질문 설계, 대화로 필드 채우기, 모르는 값 표시 | 사용자 발화 | `Profile` |
| C | ③ 혜택 수집 에이전트 | 소스 파싱, 조건을 기계 판독 형태로 정규화 | 웹 문서 또는 시드 | `Benefit[]` |
| D | ④ 자격 매칭 에이전트 | 조건 대조 로직, 판정 근거 문장 생성 | `Profile`, `Benefit[]` | `Verdict[]` |
| E | ⑤ 서류·마감 에이전트 | 체크리스트, 신청 문구 초안, 마감 계산 | `Verdict[]` | `Document` |

### 파트별 완료 조건

각자 아래를 만족하면 "내 파트는 끝"이라고 말할 수 있다.

| 담당 | 완료 조건 |
| --- | --- |
| A | mock 4종을 넣으면 화면이 끝까지 그려진다. 실패한 에이전트가 있어도 나머지가 표시된다 |
| B | 대화 5턴 안에 `Profile` 이 완성되고, 모르는 값이 `unknownFields` 에 들어간다 |
| C | 소스 2개에서 `Benefit` 5건 이상이 스키마에 맞게 나온다. `conditions` 가 기계 판독 가능하다 |
| D | 같은 `Profile` 에 대해 판정이 항상 같다. 모든 판정에 `reasons` 가 하나 이상 붙는다 |
| E | `eligible` 건마다 체크리스트와 문구 초안이 나오고, `dDay` 가 코드 계산으로 맞다 |

## 병렬 개발 규칙

### mock 을 먼저 만든다

각 파트는 **자기 출력의 mock JSON 을 가장 먼저 커밋한다.** 로직보다 먼저다.

```text
mocks/
├── profile.sample.json
├── benefits.sample.json
├── verdicts.sample.json
└── document.sample.json
```

A 는 이 mock 만으로 화면을 끝까지 만든다.
D 는 C 를 기다리지 않고 `benefits.sample.json` 으로 개발한다.
**아무도 남을 기다리지 않는다.**

### 스키마를 바꿔야 할 때

혼자 바꾸면 통합에서 깨진다. 절차를 지킨다.

1. 팀 채널에 "무엇을 왜 바꾸는지" 한 줄로 올린다
2. 영향받는 담당자가 확인한다
3. 이 문서와 mock 파일을 같이 고친다

### 통합 시점

**혼자 완벽하게 만들고 마지막에 붙이지 않는다.** 중간에 한 번 붙여본다.

| 시점 | 할 일 |
| --- | --- |
| 착수 + 30분 | 스키마 확정, mock 4종 커밋 |
| 중간 | mock 대신 실제 출력으로 한 번 연결해 본다 |
| 통합 이후 | 데모 시나리오로 리허설. 여기서부터 새 기능을 넣지 않는다 |

시간 배분은 팀 상황에 맞게 정한다. 다만 **리허설 시간을 반드시 남긴다.**

## 리스크와 후퇴 경로

| 리스크 | 후퇴 경로 | 판단 시점 |
| --- | --- | --- |
| 크롤링이 막힘 | C 가 시드 JSON 으로 전환. 실시간 수집을 버린다 | 막히는 순간 즉시 |
| 멀티에이전트 조율이 안 붙음 | ②③④⑤ 를 순차 함수 호출로 축소. [숨은 지원금 헌터](../ideas/2026-09-09-숨은-지원금-헌터.md) 형태의 단일 흐름으로 후퇴 | 통합이 두 번 실패하면 |
| LLM 응답이 스키마를 안 지킴 | 구조화 출력 강제. 실패 시 mock 으로 대체해 화면은 계속 뜨게 한다 | 설계 단계에서 미리 |
| 시간 부족 | ⑤ 의 신청 문구를 버리고 체크리스트만 남긴다 | 리허설 전 |

**후퇴 경로를 미리 정해두는 것이 이 표의 목적이다.**
당일에 "어떻게 하지"를 논의하면 그 논의 시간에 데모가 죽는다.

## 화면에 고정할 문구

법적·윤리적 안전장치다. 개발 초기에 넣고 끝까지 둔다.

- 판정 결과 옆: `해당 가능성 안내이며 최종 확인은 신청 기관에서 하셔야 합니다`
- 혜택 카드 하단: `정보 확인일 {fetchedAt}`
- 금액 옆: `실제 지급액은 심사 결과에 따라 달라질 수 있습니다`

표현은 `신청 가능` 대신 `해당 가능성 있음`, `불가` 대신 `해당 없음` 으로 통일한다.

## 개인정보 처리

- 프로필은 **세션 범위로만** 두고 서버에 저장하지 않는다
- 주민등록번호, 신분증 이미지, 계좌번호는 **입력받지 않는다**
- 데모는 가상 프로필로 진행한다

## 데모 시나리오

### 30초 버전

청년 프로필을 몇 번의 대화로 채운다.
화면에 혜택 카드가 쌓이고, 그중 셋이 초록으로 뜨며 **합계 금액이 상단에 찍힌다.**
카드 하나를 열면 판정 근거와 서류 체크리스트, 신청 문구 초안이 이미 준비되어 있다.

### 확장 버전에서 보여줄 것

- 프로필의 한 값을 바꾸면 판정이 뒤집히는 장면
- `needs_confirm` 카드에서 "왜 확인이 필요한지" 근거가 표시되는 장면
- 마감이 가까운 건이 위로 올라오는 장면

## 확인 못 한 것

아래는 착수 전에 각자 확인해야 한다. **지금 단정하지 않는다.**

- 복지로, 정부24, 온통청년의 공식 API 제공 여부와 이용 조건
- 각 소스의 크롤링 허용 범위 (`robots.txt`, 이용약관)
- 사용할 LLM 의 구조화 출력 지원 방식과 요금
- 청년 지원금 사업별 최신 조건과 금액

특히 **혜택 조건과 금액은 실제 공고를 근거로 넣어야 한다.**
데모 데이터라도 틀린 숫자를 화면에 띄우면 발표에서 지적받는다.

## 착수 회의 안건

이 문서를 열고 순서대로 정하면 된다.

1. 스키마 4종 확정 (가장 중요)
2. 담당 배정 (A~E 중 누가 무엇을)
3. 혜택 소스 2~3개 선택
4. 기술 스택 확정 (LLM, 프론트, 저장 방식)
5. 리포지토리와 브랜치 전략
6. 통합 시점 합의
7. 데모 시나리오에 쓸 가상 프로필 확정
