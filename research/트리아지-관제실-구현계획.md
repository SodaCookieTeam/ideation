# 트리아지 관제실 구현 계획

[생활 알림 트리아지 관제실](../ideas/2026-09-09-생활-알림-트리아지-관제실.md)을 본선에서 실제로 만들 때의 구현 계획입니다.

원본 아이디어의 약점 하나를 보완하는 것이 이 문서의 목적입니다. 원본은 5개 에이전트를 **한 방향 고정 파이프라인**으로 돌립니다. 하루 구현에는 옳은 선택이지만, 심사에서 "이게 에이전트인가, 5단계 함수 호출인가"라는 질문을 막을 수 없습니다. 탐색, 재계획, 외부 행동이 없기 때문입니다.

두 가지를 추가해 이 문제를 없앱니다.

1. **라운드형 반박** — 계산관과 미룸 변호인이 한 번씩 주고받지 않고, 근거 재탐색을 걸고 여러 라운드를 돈다. 판정이 도중에 뒤집힌다.
2. **행동 실행과 완료 후 재판정** — 행동 카드가 문안 생성에서 끝나지 않고 실제 산출물을 만들고, 처리 완료를 입력하면 등급을 다시 계산한다.

원본 문서의 문제 정의, 5인 역할 분담, 시연 컨셉은 그대로 유지합니다. 원본을 대체하지 않으며, 기능 범위 변경은 팀 논의 후 원본에 반영할 사항입니다.

## 무엇이 달라지는가

| 항목 | 원본 | 이 계획 |
| --- | --- | --- |
| 계산관과 미룸 변호인 | 1회 주고받고 판정 확정 | 최대 3라운드, 근거 재탐색 요구 가능 |
| 판정 변경 | 없음 | 라운드 중 등급이 실제로 바뀌고 화면에 기록됨 |
| 탐색 | 없음 | 반박이 걸리면 입력 뭉치를 재탐색해 반대 근거를 찾음 |
| 행동 | 문안 텍스트 생성 | `.ics` 파일, 체크리스트, 문안을 실제 산출물로 생성 |
| 완료 후 | 없음 | 처리 완료 입력 시 재판정, 관련 건 등급 재계산 |
| 실패 처리 | 없음 | 라운드 상한, 무승부 규칙, 판정 보류 상태 |

에이전트성 관점에서 `탐색 → 판단 → 행동 → 재계획`이 모두 채워집니다.

## 보완 1: 라운드형 반박 루프

### 왜 필요한가

원본의 핵심 통찰은 "근거를 못 내면 미룸 변호인이 이긴다"입니다. 이 승패 규칙이 회색 판정을 만들어냅니다. 여기에 **재탐색**을 붙이면 판정이 한 번에 정해지지 않고 근거 싸움이 됩니다.

실제로 자주 일어나는 상황이 이걸 정당화합니다. 관리비 고지서가 D-1이라 빨강으로 올라갔는데, 같은 문자 뭉치 안에 3일 전 자동이체 등록 완료 문자가 이미 있는 경우입니다. 단방향 파이프라인은 이걸 잡지 못합니다.

### 라운드 규칙

```text
라운드 1
  계산관    주장: D-1, 미납 시 가산금 발생, 등급 빨강
  변호인    반박: 자동이체 또는 납부 완료 근거가 입력에 있는지 확인 요구

라운드 2
  계산관    재탐색: 입력 뭉치에서 같은 발신자·같은 금액·이전 날짜 건 검색
            발견: 자동이체 등록 완료 문자
            수정 주장: 등급 회색으로 하향, 근거 문장 첨부
  변호인    수락

판정 확정  회색, 판정 근거 2건, 라운드 2회
```

- 최대 3라운드. 상한에 걸리면 **판정 보류**로 남기고 노랑으로 표시한다. 억지로 확정하지 않는다.
- 재탐색은 LLM이 새 사실을 만들어내는 것이 아니라 **이미 들어온 입력 안에서만** 찾는다. 근거 문장을 인용하지 못하면 재탐색 실패로 처리한다.
- 등급 변경 이력을 카드에 남긴다. 화면에서 `빨강 → 회색`으로 바뀐 흔적이 보여야 한다.
- 승패 판정은 코드가 한다. LLM은 주장과 반박 텍스트만 생성한다.

### 재탐색이 유효한 근거 유형

코드로 검증 가능한 것만 인정합니다. 각 유형은 입력에서 원문 문장을 찾아야 성립합니다.

| 반박 근거 | 성립 조건 | 결과 |
| --- | --- | --- |
| 이미 납부·이체 완료 | 같은 발신 주체, 같은 금액, 더 이른 날짜의 완료 문구 | 빨강에서 회색으로 하향 |
| 기한 없음 | 날짜 필드 추출 실패 또는 기한 문구 부재 | 회색 |
| 금액 없음 또는 0 | 금액 필드 부재 | 회색 |
| 행동 불필요 | 안내·확인 문구만 있고 요구 행동 없음 | 회색 |
| 중복 발송 | 같은 발신·같은 금액·같은 기한의 재발송 | 하나만 남기고 나머지 회색 |
| 기한 이미 경과 | 기한이 오늘보다 과거 | 노랑, 사후 대응 안내 |

`이미 납부 완료`와 `중복 발송`이 재탐색으로만 잡히는 유형이며, 라운드 구조의 존재 이유입니다.

### 무승부와 보류

- 계산관이 근거를 못 내면 변호인 승리, 회색.
- 변호인이 반박 근거를 못 찾으면 계산관 승리, 등급 유지.
- 양쪽 모두 근거가 있고 3라운드에 도달하면 **보류**, 노랑. 사용자에게 직접 확인을 요청한다.

보류를 만드는 이유는 이 도구가 회색을 만들어내는 만큼 **모르는 것을 모른다고 말할 자리**도 필요하기 때문입니다.

## 보완 2: 행동 실행과 완료 후 재판정

### 행동 산출물

행동 카드 작성관이 텍스트만 내지 않고 세 가지를 만듭니다.

| 산출물 | 내용 | 구현 |
| --- | --- | --- |
| `.ics` 일정 파일 | 기한 하루 전과 당일 알림 | 코드로 생성, 다운로드 |
| 처리 체크리스트 | 무엇을 어디서 어떻게 | 항목별 체크 가능 |
| 보낼 문안 | 문의 문장 또는 전화 스크립트 | LLM 생성, 복사 버튼 |

`.ics`는 원본에서 `있으면 좋음`이었으나 이 계획에서는 **필수**입니다. 행동이 파일로 나와야 실행으로 인정됩니다.

### 완료 후 재판정

사용자가 처리 완료를 누르면 파이프라인이 다시 돕니다.

```text
사용자    관리비 고지서 처리 완료 체크
   │
   ▼
재판정   해당 건: 빨강 → 완료
         관련 건 재탐색: 같은 발신·같은 금액의 독촉 문자 2건 발견
         두 건을 노랑에서 회색으로 하향
   │
   ▼
화면     오늘 할 일 2건 → 1건
```

한 건의 처리가 다른 건의 등급을 바꿉니다. 이것이 재계획이며, 화면 숫자가 다시 줄어드는 장면이 하나 더 생깁니다.

## 아키텍처

오케스트레이터는 여전히 코드입니다. LLM에 조율을 맡기지 않습니다. 달라진 점은 파이프라인이 직선이 아니라 **루프를 포함한 상태 머신**이라는 것입니다.

```text
입력 (문자 뭉치 붙여넣기 / 고지서 사진)
   │
   ▼
① 판독관        건별 구조화, 원문 근거 보존
   │
   ├──────────────┐
   ▼              ▼
② 사칭 검증관   ③ 기한·금액 계산관
   │              │
   │ 사칭          │ 시급 주장 + 등급 제안
   │ → 격리        ▼
   │           ┌───────────────┐
   │           │  라운드 루프   │  최대 3회
   │           │  ③ ↔ ④       │
   │           │  재탐색 포함   │
   │           └───────┬───────┘
   │                   ▼
   │            판정 확정 또는 보류
   │                   ▼
   │            ⑤ 행동 카드 작성관
   │                   │
   ▼                   ▼
빨강 / 노랑 / 회색 관제 화면
                       │
              사용자 처리 완료 입력
                       │
                       └──→ 재판정 (③ 재실행)
```

### 상태

건 하나의 상태 흐름입니다.

`입력 → 구조화 → 사칭검사 → 라운드중 → 판정확정 | 보류 → 행동생성 → 완료`

사칭 판정 건은 `격리`로 빠지고 라운드에 들어가지 않습니다.

## 데이터 스키마

병렬 개발의 전제입니다. **개발 시작 전 30분 안에 이 스키마를 못 박고**, 각자 목 데이터로 독립 개발합니다.

### 건 (item)

```json
{
  "id": "item-003",
  "raw": "[관리비] 9월분 관리비 152,000원 납부기한 9월 10일",
  "sender_claim": "관리사무소",
  "doc_type": "고지서",
  "due_date": "2026-09-10",
  "amount": 152000,
  "links": [],
  "evidence": {
    "due_date": "납부기한 9월 10일",
    "amount": "152,000원"
  }
}
```

`evidence`가 핵심입니다. 모든 추출 값은 원문 문장을 함께 남깁니다. 근거 없는 값은 판정에 쓰지 않습니다.

### 라운드 (round)

```json
{
  "item_id": "item-003",
  "round": 2,
  "claim": {
    "by": "calculator",
    "grade": "red",
    "reason": "기한 D-1, 미납 시 가산금 발생",
    "evidence": ["납부기한 9월 10일"]
  },
  "rebuttal": {
    "by": "advocate",
    "type": "already_paid",
    "reason": "자동이체 등록 완료 근거 존재",
    "evidence": ["9월 7일 자동이체 등록이 완료되었습니다"],
    "found_by_research": true
  },
  "resolution": "downgrade_to_gray"
}
```

### 판정 (verdict)

```json
{
  "item_id": "item-003",
  "grade": "gray",
  "grade_history": ["red", "gray"],
  "rounds": 2,
  "decided_by": "advocate_win",
  "confidence": "high",
  "actions": []
}
```

`grade_history`가 있어야 화면에서 판정이 뒤집힌 흔적을 보여줄 수 있습니다.

## LLM과 코드의 경계

발표에서 신뢰를 잃지 않기 위한 원칙입니다.

| 담당 | 하는 일 |
| --- | --- |
| 코드 | 날짜 계산, D-day, 가산금 산술, 라운드 승패 판정, 등급 확정, 중복·금액 일치 비교, `.ics` 생성 |
| LLM | 텍스트 구조화, 사칭 의심 사유 서술, 주장·반박 문장 생성, 문안 작성 |

숫자와 판정은 전부 코드입니다. LLM이 계산한 금액을 화면에 띄우지 않습니다.

## 5인 역할 분담

원본의 분담을 유지하되 라운드 루프와 재판정 담당을 명확히 합니다.

| 담당 | 맡는 것 | 추가된 책임 |
| --- | --- | --- |
| A | 오케스트레이터, 관제 3칸 UI, 토글 | 라운드 상태 머신, 등급 변경 애니메이션, 재판정 트리거 |
| B | ① 판독관 | 원문 근거 보존 스키마 |
| C | ② 사칭 검증관 | 격리 뷰, 판정 근거 표시 |
| D | ③ 계산관 | 재탐색 함수, 라운드별 주장 생성 |
| E | ④ 미룸 변호인, ⑤ 행동 카드 | 반박 유형 6종, 승패 규칙, `.ics` 생성 |

의존 관계상 A와 E가 라운드 루프의 핵심입니다. D의 재탐색 함수와 E의 반박 유형은 **같은 스키마를 공유**하므로 둘이 먼저 합의해야 합니다.

## 하루 작업 순서

정확한 대회 일정은 확인하지 못했으므로 상대 시간으로 적습니다. 아이디어 확정 직후를 `T+0`으로 둡니다.

| 시간 | 작업 | 담당 |
| --- | --- | --- |
| T+0 ~ 0:30 | 스키마 확정, 목 데이터 12건 작성, 저장소·브랜치 세팅 | 전원 |
| 0:30 ~ 2:00 | 판독관 파싱, 사칭 규칙, 계산 코드, UI 골격 병렬 착수 | B C D A |
| 2:00 ~ 3:30 | 라운드 루프와 반박 유형 6종 구현 | D E A |
| 3:30 ~ 4:30 | 3칸 관제 화면 연결, 등급 변경 표시 | A |
| 4:30 ~ 5:30 | 행동 카드, `.ics` 생성, 완료 후 재판정 | E A |
| 5:30 ~ 6:00 | 미룸 변호인 토글 구현 | A E |
| 6:00 ~ 7:00 | 통합, 12건 시나리오 고정, 실패 흐름 처리 | 전원 |
| 7:00 ~ 8:00 | 데모 리허설 3회, 발표 준비 | 전원 |

병렬 개발의 조건은 원본과 같습니다. **스키마를 먼저 고정하면** B의 파서가 늦어도 C, D, E는 목 JSON으로 계속 갑니다.

## 3분 데모 시나리오

원본의 토글 장면을 유지하고, 판정 반전과 재판정 장면을 추가합니다.

| 시간 | 장면 |
| --- | --- |
| 0:00 ~ 0:20 | 실제 문자 12건을 통째로 붙여넣는다. 카드가 쌓이고 전부 노란불이다. |
| 0:20 ~ 0:45 | 사칭 검증관이 지원금 신청 문자 1건을 링크 도메인 불일치로 격리한다. 판정 근거를 펼쳐 보인다. |
| 0:45 ~ 1:15 | 계산관이 관리비 고지서를 D-1, 가산금 근거로 빨강으로 올린다. 계산식을 펼쳐 코드 산출임을 보여준다. |
| 1:15 ~ 1:50 | **라운드 장면.** 변호인이 납부 완료 근거를 요구하고, 계산관이 입력을 재탐색해 자동이체 완료 문자를 찾아낸다. 빨강 카드가 회색으로 내려가고 `빨강 → 회색` 이력이 남는다. |
| 1:50 ~ 2:10 | 변호인이 나머지 건을 기한 없음, 금액 없음, 중복으로 회색으로 끌어내린다. 상단이 `12건`에서 `오늘 할 일 2건`으로 바뀐다. |
| 2:10 ~ 2:30 | **재판정 장면.** 남은 빨강 1건의 `.ics`를 내려받고 처리 완료를 체크한다. 관련 독촉 문자 2건이 자동으로 회색으로 내려가며 `오늘 할 일 1건`이 된다. |
| 2:30 ~ 2:50 | **토글 장면.** 미룸 변호인을 끈다. 회색이 전부 노란불로 되돌아오며 화면이 다시 지저분해진다. |
| 2:50 ~ 3:00 | 다시 켜고 마무리. "구조를 나눈 이유가 이 토글입니다." |

핵심 장면이 세 개입니다. **판정이 뒤집히는 순간**, **처리 하나가 다른 건을 바꾸는 순간**, **토글로 구조의 가치를 증명하는 순간**입니다.

## 안전장치

이 제품의 가치는 `무시해도 됩니다`를 말하는 것이고, 그것이 동시에 가장 큰 위험입니다.

| 위험 | 대응 |
| --- | --- |
| 회색 오판으로 사용자가 연체함 | 회색 카드에도 판정 근거와 라운드 이력을 항상 붙인다. 회색 목록을 접지 않고 언제든 펼 수 있게 둔다. |
| 진짜 고지서를 사칭으로 격리함 | 표현을 `차단`이 아니라 `의심, 공식 앱에서 직접 확인`으로 고정한다. 격리도 삭제가 아니라 별도 칸이다. |
| 재탐색이 없는 근거를 만들어냄 | 원문 문장 인용을 강제하고, 인용 실패 시 재탐색 실패로 처리한다. |
| 가산금 요율이 기관마다 다름 | 요율을 화면에 명시하고 계산 과정을 펼쳐 보인다. 실제 요율은 확인하지 못했다. |
| 라운드가 무한히 돌거나 지연됨 | 상한 3회, 라운드별 타임아웃, 초과 시 보류 처리. |
| 개인정보가 그대로 들어옴 | 세션 범위로만 두고 저장하지 않는다. 데모는 직접 만든 샘플을 쓴다. |

화면에 `정보 제공이며 최종 확인은 사용자 몫`을 고정 문구로 둡니다.

## 심사 질문 방어

예상되는 질문과 답할 근거입니다.

**이게 왜 에이전트인가.**
계산관이 입력을 재탐색해 반대 근거를 찾고 자기 주장을 철회합니다. 처리 완료 하나가 다른 건의 등급을 다시 계산합니다. 판정 결과가 도중에 바뀌는 것을 화면에서 보여드립니다.

**LLM 하나로 프롬프트만 잘 쓰면 되지 않는가.**
토글을 끄면 그 결과가 나옵니다. 전부 노란불이 되고 사용자는 아무것도 얻지 못합니다. 이것이 구조를 나눈 이유입니다.

**무시해도 된다고 했는데 틀리면 누가 책임지는가.**
회색 판정에도 근거와 라운드 이력이 전부 남고 접히지 않습니다. 확신이 낮으면 회색이 아니라 보류로 보냅니다. 최종 확인은 사용자 몫임을 화면에 고정합니다.

**숫자는 믿을 수 있는가.**
날짜와 금액 계산은 전부 코드이며 계산식을 펼쳐 보입니다. LLM은 설명 문장만 씁니다.

## 하루 MVP 범위

### 반드시 만드는 것

- [ ] 문자 뭉치 붙여넣기와 건별 구조화, 원문 근거 보존
- [ ] 사칭 의심 격리와 판정 근거 표시
- [ ] D-day와 손해액 코드 계산
- [ ] 라운드형 반박 루프, 반박 유형 6종, 상한 3회
- [ ] 재탐색으로 판정이 뒤집히는 흐름과 등급 변경 이력
- [ ] 빨강·노랑·회색·격리·보류 관제 화면
- [ ] 행동 카드, `.ics` 생성, 처리 체크리스트
- [ ] 처리 완료 후 관련 건 재판정
- [ ] 미룸 변호인 끄기 토글

### 시간이 남으면

- [ ] 고지서 사진 입력
- [ ] 판정 근거 접기·펴기
- [ ] 라운드 진행 과정 실시간 표시

### 이번에 하지 않는 것

- 문자 자동 수신과 실제 알림 발송
- 실제 납부, 이체, 기관 제출
- 사칭 여부 확정과 신고 대행
- 저장, 로그인, 계정
- 실제 가산금 요율 데이터 연동

## 성공 기준

데모가 합격선을 넘었는지 판단하는 기준입니다.

1. 12건이 `오늘 할 일 2건`으로 줄어든다.
2. 최소 1건의 판정이 라운드 중에 뒤집히고 그 흔적이 화면에 남는다.
3. 처리 완료 1건이 다른 건의 등급을 바꾼다.
4. 토글로 전부 노란불이 되는 것을 보여준다.
5. 어떤 숫자도 LLM이 계산한 것이 아니라고 말할 수 있다.

1과 4만 되면 원본과 같습니다. 2와 3이 이 계획의 핵심이며, **둘 중 하나라도 빠지면 에이전트성 방어가 약해집니다.**

## 확인하지 못한 것

- 기관별 가산금과 연체료 실제 요율
- 통신사·기관별 문자 포맷의 실제 분포
- 사칭 판정 규칙의 실제 정확도
- 재탐색으로 잡히는 `이미 납부 완료` 사례의 실제 빈도
- 대회 당일 개발 가능 시간과 발표 시간 배분

요율과 포맷은 데모용 샘플로 대체하고, 화면에 가정임을 표시합니다.
